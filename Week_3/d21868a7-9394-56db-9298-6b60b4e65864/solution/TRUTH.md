## Journeys (ideal end-to-end flow)

1. **Ordering before a heatwave** (brief: Journeys 1, DP-11..17, DP-70). Lin signs in at `/sign-in` (Sign-in status `Signing in.`) → lands on `/grower` (or on the `return` path when `shared/roles.ts landingFor` allows it: one leading `/`, not `//` or `/\`, a page route of her role); region "Allocation" reads `40.000 ML of 40.000 ML left` beside her order list. She follows a window's Order link → `/grower/orders/new?window=<id>`; picks T4-15 from the Turnout combobox (select-only combobox whose options exist only while open, decided: so the page's only closed-state options are search suggestions), types a volume; 300 ms after the last keystroke the form asks `GET /api/orders/quote?window=…&volume_ml=…&turnout=T4-15` (brief: Interactions; no quote while no window is selected or Volume is empty). Flow rate shows `<rate> ML/day` from the successful reply to the latest turnout, window and volume, and a bare dash otherwise. Window remaining shows `<remaining> ML` from whichever server reply for the selected window arrived last (a successful latest quote, `GET /api/windows/<id>` read on selection and every 2 s, or a 409 `window_full` body), and a dash only while no window is selected. A volume above T4-15's max volume (25.000 ML in a 24-hour window, `server/decimal.ts turnoutMaxVolume`) shows `More than T4-15 can pass in this window: 25.000 ML.` under Volume. A reply keyed to an older input is dropped (`client/pages/OrderForm.tsx`); Window status shows the server's label; the selected window stays selected and listed even once it is `closed` (Place order disabled). Every edit writes the draft to `sessionStorage` under `ditchbook:order-draft:<grower id>`. If her session ends on the form, the next 401 marks that draft ended and sends her to `/sign-in?return=%2Fgrower%2Forders%2Fnew%3Fwindow%3D<id>`; signing in again as Lin restores every field once with Order status `Your session ended. Your order is as you left it. Check it and place it again.` (another grower finds an empty form); nothing is placed. Place order (`aria-disabled` and inert while pending or while the window is not orderable; one press, one request) → Order status `Placing your order.` → browser on `/orders/ORD-000NN`, Order status `Order ORD-000NN scheduled.`, status badge `Scheduled`. Provider: one `water_order` row (scheduled), `delivery_window.committed_milli` and `allocation.debited_milli` both up by the volume in one transaction, one open start card for the gate operator. At the window's `closes_at`, the first API request lapses its requested and scheduled orders (closed, `conflict` `lapsed`, volume, allocation and start card released; `server/orders.ts lapseClosedWindows`, brief: Lapse at the window's close); the same step queues one lapse notice per grower and window (`Ditchbook lapse: <channel>, <label>`, one line per lapsed order). The Order page and Your orders then announce `Order ORD-000NN lapsed when the window closed.` in Order status and show `Lapsed when the window closed.`; any other server change announces `Order <n> is now <label>.` (`client/lib.ts useOrderChanges`).
2. **Two growers chase the last megalitres** (brief: Journeys 2, DP-18..20). Both POSTs are judged one after another under one Postgres advisory lock: validation first (range, then outlet limit, then the grower's allocation as 422 on `volume_ml`), then 409s (`too_early`, `window_closed`, `turnout_busy`, `window_full`). Winner: 201 → order page. Loser: 409 `window_full` with `remaining_ml`; nothing stored for the order; Window remaining shows that `remaining_ml` and the Allocation counter re-reads `GET /api/me/allocation`; alertdialog "Capacity taken" (brick top border, heading `Capacity taken`, body `Another order took the last of this window's capacity. Nothing was debited from your allocation.`, button `Back to the order`; focus trapped, returns to Place order). Mailpit: one message `Ditchbook: capacity taken on <channel>, <label>` to the loser, from `MAIL_FROM`, with the copy, the requested volume and `Your allocation is unchanged at <remaining allocation> ML.` (the loser's own figure at judgement). A 422 allocation or outlet-limit refusal sends none.
3. **A stroke from the channel bank** (brief: Journeys 3, DP-21..28). `/field`: card `article "Gate card <turnout>"` with `group "Window status <turnout>"` holding the server's `window_status` label (an upcoming start card keeps its dwell; committing it answers `This window is not open yet.`); the `list "Gate cards"` is always present (an empty one says no cards are held); press and hold (pointer, touch or Space) the cobalt gate glyph; progressbar 0→100 linearly over 1 s (25/50/75 at quarters); release, pointer cancel or leaving the control, lost pointer capture, blur or the page becoming hidden → 0 at once, `Released early. Stroke not sent.`, and a later Space release does nothing; at 1 s the POST is sent: `Stroke sent. Waiting for the store.`, card shows `Waiting for the store`. Store confirms → 200: card spent with region "Stroke record <turnout>", `Stroke stored for <turnout>. Flow now <flow> ML/day.`, Channel flow counts up over 0.6 s, new Finish card (rate → 0.000) appears. Provider: card open→waiting-for-store→spent; MinIO `strokes/<card id>.json` (operator code only); order running. Store down → 202, `The evidence store is not answering. The stroke will count once it is stored.`; worker retries every 5 s.
4. **A mid-window cut** (brief: Journeys 4, DP-35..39). Board → select cell → R (or button) → dialog "Publish restriction" (Cap (ML/day), Reason, Publish, Cancel) → 201 with `effective_at` = publish instant truncated to the UTC minute; cap volume = (table cap × m_before + effective cap × m_after) ÷ 1440, rounded once half-up (`server/decimal.ts capVolume`, brief: One conversion rule) → `/restrictions/<id>` with Board status `Restriction published for <channel>, <label>. <n> orders moved to requested.`, cap and moved orders, same on reload. Scheduled orders kept earliest `scheduled_at` first while they fit; the rest → requested, `conflict: restriction`, volume and allocation released, open start card deleted. Notices queued in the same transaction, one per affected grower; open screens poll every 2 s (decided: inside the 5 s rule).
   Ration (brief: Journeys 4, DP-66..69): Orders panel → `Ration window` (shown while the server status is not `closed` and a requested order exists) → alertdialog `Ration <window label>` with `Share <remaining> ML among <n> requested orders in proportion to what each asked for.` → Ration (cobalt) → Board status `Rationing.` (rows and counters held, Ration window and row actions `aria-disabled`) → `Window rationed. <scheduled> orders scheduled, <left> left requested.`; rows take the reply's shares, a rationed Volume cell adds `Asked <requested_ml> ML`, the Order page adds `Rationed from <requested_ml> ML.` Provider: candidates in order-number order, demand = lowest of volume, the turnout's max volume and the grower's remaining allocation less earlier demands, shares rounded down with leftover thousandths by largest remainder (`server/ration.ts shares`, the one place); scheduled shares debit window and allocation, issue start cards, set `rationed`; one ration notice per grower with a candidate.
5. **A handover mid-flow** (brief: Journeys 5, DP-29..32). Board → Gate cards expander → `Remove holder <turnout>` → `Handing over.` → `Gate card for <turnout> handed to <code>.` Successor: named standby, then rostered operator, skipping erased and the removed operator (`server/cards.ts successorFor`, the one place). 6. **Two dispatchers and a capacity table** (brief: Journeys 6, DP-40..46).    Review page (brief: Screens and layout, DP-82): Channel totals has one row per covered window (Channel, Window, Cap volume (ML), Committed (ML), Delivered (ML), Remaining (ML)); beside Mailed packs at 1280, above it at 768, one stacked block per row at 375 with table, row and cell roles kept.

## Decisions where the brief is silent

- Window record also carries `restriction_id`; card and order records also carry `grower_name` (the field card and the Window orders Grower column show it).
- A grower's quote or order on a window of a channel where they hold no turnout answers 404 (brief: API precedence, "another grower's … window channel").
- An unknown `/api` path answers 404 before the session check (brief: Server boundary).
- The board grid keeps every window of the season (brief: Screens and layout, "Cells are ordered by channel (rail order), then by window opening time"). So that a long season stays usable within the brief's three seconds (Browser support and performance), each cell is memoised on the figures it shows, and grid rows off screen skip layout and paint (`content-visibility: auto`) until they are scrolled to. The rows keep their size, accessible names and Tab order (decided). The capacity table keeps native table layout: measured, content-visibility made it slower, not faster.
- Gate cards list newest first (decided: the card just issued to the operator is the one they act on next, and it stays on the first screen of a long day's list); the dwell, the wait and the stroke record share one slot at least as tall as the dwell, so a card never shrinks under the thumb.
- New window ids `W-<channel code>-<4-digit serial>`; card and restriction ids are integers; seed revision 1 saved by `District seed`.
- Conflict notices also go out when a dispatcher's schedule is refused with `window_full` (brief: "one per order refused with window_full").
- Restriction kept/moved uses "while it fits" literally: the first scheduled order that does not fit and every later one move.
- The card record also carries `handed_over` (true once succession has moved it), so a field view can tell a handed-over card from a newly issued one.
- Every page route of `brief: Screens and layout, Pages per role` lives in `shared/roles.ts`; the server redirects a signed-out page load to `/sign-in?return=<encoded path and query>` and a signed-in load of another role's route (or `/sign-in`) to the home route; unknown paths show `Page not found` signed in or out.
- The ration takes the district advisory lock every placement, schedule and publish takes, so it is judged one after another with them (brief: "the same window-then-allocation order"; one lock orders them more strictly still).
- A ration notice opens with one sentence naming the channel and window, then the published lines.
- Retries every 5 s; SMTP/S3 attempts time out after 5 s.
- Repeated-hour mark (brief: Window instants, hours and labels): an instant whose district clock reading recurs one hour later is the first pass (` AEDT`), one hour earlier the second pass (` AEST`), decided in `server/time.ts` and used by every label.
- Search (brief: Search reach table): turnout and grower details list turnouts by channel in rail order and then by code; grower suggestions are matched in grower-id order before the label sort.
- The lapse notice opens with one sentence naming the channel and window, then the published lines (decided: the ration notice's shape).
- The Order page wraps its status badge in `group "Order state"`; the Notices expander shows each notice's kind (Conflict, Restriction, Ration, Lapse) before the grower name.
- Bucket (brief: Configuration and secrets, instruction.md:433): the app writes only to `S3_BUCKET`; when a write finds that bucket missing (`NoSuchBucket`) once the store answers, it creates exactly that bucket and retries the write (`server/store.ts putObject`).
- A lost Postgres connection never ends the process (brief: Server boundary, "If Postgres is unreachable … the server still listens, answers 503 `database_unavailable`, and retries"): every pooled client carries an error listener, a client that broke inside a transaction is discarded rather than returned to the pool, and that request answers 503 (`server/db.ts tx`). Seen in the iteration-3 trial: every app backend was terminated mid-suite, and the unhandled client `error` event exited all three instances.
- The store client speaks `node:http`, not `fetch` (brief: Services, "the same `S3_ENDPOINT` … as read at start"): `fetch` refuses ports on the Fetch standard's blocked list (port 9 among them), so it could never reach a store configured on such a port.

**Open (3 Nov 18:00 refreeze, test harness, no product change possible).** The new `lapse_slot` (`test_app.py` L1563-1583) returns the soonest *unused* (instance, channel) pair and uses a used pair only when no unused pair is left. It never compares the wait against `LAPSE_WAIT_S`. Four tests call `lapse_scene`, but only the three C-12 pairs have a free hour soon. The seeded W-L4-B blocks C-L4 until H + 46 h and W-09-A blocks C-09 until H + 11 h (brief: Seed data, Windows), and unused C-L4/C-09 pairs always remain. So once the near C-12 pairs are spent, the slot chosen is hours away and `pytest.fail("no channel hour is free for a lapse window")` fires (seen in `test_board_follows_window_close` and `test_window_status_follows_server`). A used C-12 pair, about an hour out, would have been inside the limit. Fix in the harness: prefer an unused pair only while its wait is within `LAPSE_WAIT_S`. The previous version (soonest pair overall) scored these tests as passing.

Earlier, resolved by the 3 Nov second refreeze (no product change): `lapse_scene` now gives its window a cap of the turnout's own max rate and orders cap volume less 0.001 ML; `test_turnout_outlet_limit` uses a 120.000 ML/day window; the pack tests name `To` with `exact=True`; `test_typed_caps_survive_live_refresh` waits with `expect_request`; `test_wf_regulator_review_live` only asserts the link is absent while the pack is unmailed.
